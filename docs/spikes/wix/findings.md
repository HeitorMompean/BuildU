## 3. Consequences for the provider-neutral design

These follow from the findings and inform R11-G/R12-M. They don't change the architecture.

1. **"Paid" is decided only by server-side reconciliation of order + transactions** (F-09, F-10), never by return URLs (F-07) or webhook content alone (F-12, F-16). Webhooks are triggers to reconcile.
2. Reconciliation must match: `order.checkoutId == stored wixCartId`; `order.purchaseFlowId == stored purchaseFlowId`; currency (F-05); total; and transaction evidence of an online `APPROVED` payment for the full amount (F-10). Any mismatch goes to admin review, never to `paid`.
3. Cart creation must set `manualPaymentDisabled=true`, `lockCouponCode=true`, `lockGiftCard=true`, and `fixedQuantity=true` per item (F-03, F-11). Whether these fully prevent tampering is a sandbox proof (SP-04).
4. Money conversion: internal `amountMinor` (signed 64-bit) → Wix decimal string by the configured currency exponent. Reject currencies whose exponent exceeds 3 or amounts above Wix's `999999999` bound (F-03).
5. No provider-side idempotency means our side must write the outbox/intent record before each external call. After a timeout, re-query (Search Orders by `checkoutId`, Get Order Refundability) before any retry (F-19).
6. Account and credential model: a self-managed **Wix app** installed on the business's own site is needed for webhooks (F-12). API key vs app OAuth for REST calls must be decided (UQ-04). The configuration names in `docs/operations/configuration.md` (`WIX_APP_ID`, `WIX_WEBHOOK_PUBLIC_KEY_SECRET_ARN`, `WIX_API_KEY_SECRET_ARN`) match the app-based shape. An OAuth client secret may also be needed. This is reported for R12-M/ROOT, not changed here.
